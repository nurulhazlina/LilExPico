Activity 13 — teacher notes

Sending Data to a Live Dashboard. The board posts every sensor reading to Google Sheets over WiFi. The dashboard reads the sheet and updates itself live — from anywhere, with nothing to host.

▶ Student page ▶ Open the dashboard 📚 All teacher notes ← Activity 12 notes 📌 Pin reference
Keep this link to yourself. Unlisted and hidden from search engines, but the repository is public — anyone with the URL can read it.
Deploy the Apps Script before the lesson. The deployment takes about five minutes and requires a Google account. Do it once from your own account; then every student uses the same /exec URL. Paste it into config.py on each board, or give students the URL on a card so they can type it themselves.

What is being taught

  • One idea: data reaches the browser without a server you run. The board sends JSON to Google Apps Script, Google stores the row, the dashboard asks Google for it. The class does not install or maintain anything — and the dashboard updates live, in a browser tab, on any device.
  • The cloud is not magic, it is a shared notice board. The Pico cannot talk directly to the browser (both are behind different routers). The spreadsheet is the shared place: the board writes to it and the browser reads from it. That one sentence explains the whole architecture.
  • WiFi is the new hardware idea. The network module requires Pico W firmware. The board connects once on startup and stays connected for the session. This is the first time students write code that leaves the room.
  • Rate limiting is real engineering. maybe_send() checks elapsed time before posting. Posting on every loop tick would flood the network and get the Apps Script URL throttled. Students do not write this logic — they use it — but it is worth naming.
  • Reused, not re-taught: the loop, sleep, Pin, def, import, the full sensor stack from Activity 8 onwards, and config.py from Activity 11. The new code is three lines added to a program the class already understands.
  • Genuinely new: import network, urequests, json.dumps(), and the idea that an HTTP POST carries structured data. None of these need to be explained in full — the wifi_reporter.py file wraps all of them.

Setting up the Apps Script

  • Do this once, before the class. Go to script.google.com, create a new project, paste in LilEx5_AppsScript.js, deploy as a Web App: Execute as: Me, Who has access: Anyone. Copy the /exec URL.
  • The sheet is created automatically. The first POST from any board creates the spreadsheet and the SensorData tab. You do not need to create it in advance.
  • One deployment, one sheet, one class. All boards write to the same sheet. The dashboard reads the most recent row, so it shows whoever posted last. If you want each student to have their own data, deploy a separate Apps Script per student — but this is unnecessary for the class activity.
  • If you redeploy, the URL changes. Update config.py on every board and the API_URL constant at the top of LilEx5_Dashboard4.html.

WiFi requirements

  • 2.4 GHz only. The Pico W radio does not support 5 GHz. Most school networks broadcast both bands under the same name — if the board cannot connect, it is almost always on the 5 GHz band. Ask your IT department to confirm the 2.4 GHz SSID, or use a phone hotspot set to 2.4 GHz.
  • SSID and password are case-sensitive. One wrong character hangs the board at Connecting… with no error. Paste, do not type, whenever possible.
  • Captive portals will not work. If your school network requires a browser login before granting internet access, the Pico cannot complete it. A phone hotspot avoids this entirely.
  • Pico W firmware is required. Standard Pico firmware has no network module. If a student sees ImportError: no module named 'network', flash the Pico W firmware: hold BOOTSEL, plug in USB, drag the .uf2 file onto the RPI-RP2 drive. Then re-upload all files.

How to run the room

  • Put the dashboard on the projector before the lesson starts, already open and showing live data from your own board. Students who see the tiles updating before they write a line of code understand the goal immediately.
  • Walk the room once during Step 2 (editing config.py). A wrong URL or mistyped password at this stage causes silent failure later. Paste the URL from your own screen if possible.
  • The Shell is the proof. POST 200 OK — 20 fields sent appearing every five seconds means everything is working. If a student's Shell shows this, tell them to open the dashboard and watch the tiles. If it does not, the problem is WiFi or the URL — nothing else.
  • All boards write to the same sheet. The dashboard shows the most recent row from any board. Ask students to breathe on their BME280 and watch the temperature tile jump — that is the moment of the lesson.
  • The dashboard link is in three places on the student page (hero, Step 5 banner, and the Links table) and also in this file. Make sure students know to open LilEx5_Dashboard4.html, not to create their own.

Exercise answer — add a high-temperature alert

The exercise on the student page asks them to add a check: if the temperature reading in the data dict is above 30 °C, print a warning in the Shell before posting. This requires reading a value out of the data dict and using an if — both already taught.

# Exercise answer — main_dashboard.py with temperature alert added
# Changes are marked with  ← NEW

from adapter import (
    make_bme280_fields, make_ags10_fields,
    make_vcnl_fields, make_bmi323_fields,
    make_qmc_fields, make_ads_fields,
)
from wifi_reporter import WiFiReporter
import config

sensor_fields = (
    make_bme280_fields() +
    make_ags10_fields() +
    make_vcnl_fields() +
    make_bmi323_fields() +
    make_qmc_fields() +
    make_ads_fields()
)

reporter = WiFiReporter(config.WIFI_SSID, config.WIFI_PASS, config.APPS_SCRIPT_URL)
reporter.connect()

while True:
    data = {}
    for f in sensor_fields:
        f.update()
        data[f.key] = f.value

    if data.get("temp_c", 0) > 30:            # ← NEW
        print("WARNING: temperature above 30 C!")   # ← NEW

    reporter.maybe_send(data, config.REPORT_INTERVAL_MS)
Accepting itWhat to look for
The key name"temp_c" must match the key set by make_bme280_fields(). Accept any key they found by printing data first — that is good engineering.
Position of the checkAfter the data dict is built and before maybe_send(). After the send is also acceptable; before the loop is wrong (data is not ready yet).
The thresholdAny temperature that makes sense. 30 °C is the example; accept 28, 35, or whatever the student chose and can justify.
Acceptance testBreathe on the BME280 until the temperature climbs above the threshold. The warning must appear in the Shell before the next POST line.
Why this exercise It uses dict.get(key, default) — a single new method — and otherwise applies only what the class already knows: if, a comparison, and print(). The harder part is knowing that data is a dict and choosing the right key — which means reading code rather than writing it. That is the whole exercise.

Going-further answers

TaskAnswer / what to say
Change how often the board posts Edit REPORT_INTERVAL_MS in config.py. 1000 is once a second; 60000 is once a minute. Going below 1000 is possible but starts to saturate the Apps Script quota — Google rate-limits free accounts to roughly 20 000 URL fetches per day.
Print every key–value pair in the data dict for k, v in data.items(): print(k, v) — the first time most students use .items(). Good for understanding exactly what is being sent.
View the dashboard from a phone Open LilEx5_Dashboard4.html on any device connected to the internet. The Apps Script URL is already public, so no extra setup is needed. This is the payoff sentence of the whole module: the board in the lab, the dashboard on a phone across town.
Chart in Google Sheets Select the temp_c column in the SensorData tab, insert a chart, and set the chart type to Line. It updates live as new rows arrive. No code needed — that is the point.
Two boards, one sheet Both students use the same APPS_SCRIPT_URL and different WiFi credentials. Both write rows; the dashboard shows the most recent. Ask what they would need to add to tell the rows apart: a board ID field.
Send only if a value crosses a threshold Wrap maybe_send() in an if that checks a sensor reading. The board stops sending and the dashboard tiles go grey. Good conversation about “no news is news” versus “last known good” in IoT systems.

Before the lesson

  • Deploy the Apps Script from your own Google account and test it with one board before the class. Confirm the sheet appears and POST 200 OK prints in the Shell.
  • Open the dashboard on the projector and leave it running. Students who see live data before the lesson starts arrive with the right mental model already in place.
  • Confirm the classroom WiFi is 2.4 GHz and has no captive portal. If it does, arrange a phone hotspot or ask IT to whitelist the Pico's MAC address.
  • Flash Pico W firmware on any board that still has standard Pico firmware. You can check before the lesson: if import network raises an error, the firmware is wrong. Download from micropython.org/download/RPI_PICO_W/.
  • Prepare config cards. One small card per student with the WiFi SSID, password, and your /exec URL already printed. Typing a 90-character URL by hand is where most lessons go wrong.
  • Know your Apps Script quota. Google allows roughly 20 000 URL executions per day on a free account. A class of 30 boards posting every 5 seconds uses about 21 600 per hour. Keep the lesson short or raise REPORT_INTERVAL_MS to 10 000 for class use.
  • Thonny preset to MicroPython (Raspberry Pi Pico); all six sensor driver files already on the boards from Activity 8.

Teaching notes

  • Open with the dashboard already live on the projector. Ask: “Where is the data coming from?” Most will guess the board on the desk. Correct — but it went through Google first. That is the whole architecture in one sentence.
  • Draw the three hops on the board. Board → Google → Browser. Then ask why you cannot do Board → Browser directly. Both sides are behind different routers; there is no address the browser can dial. The spreadsheet is the shared place that both sides can reach. This is the one idea worth spending five minutes on.
  • The wifi_reporter.py file does not need to be read in full. Students use it the same way they use adapter.py — import it, call the methods, trust the result. The three new lines in main_dashboard.py are all they write.
  • The moment of the lesson is the tile updating. When a student breathes on the BME280 and the temperature tile on the projector moves three seconds later — through WiFi, through Google, back to the browser — that is when the data flow becomes real. Do not hurry past it.
  • Rate limiting is worth one sentence. “The board could post a hundred times a second, but Google would throttle it and the lesson would end.” maybe_send() is the professional solution. Naming it is enough.
  • Close the module here. From one LED on a pin, to a message through the air (Activity 12), to six sensors posting live to a dashboard anyone in the world can open. It is worth saying out loud.

Tier 3 — Extend: Multi-topic publisher — temperature to lilex/temp, simulated humidity to lilex/humidity, uptime to lilex/uptime. Last-will: "offline".

from umqtt.simple import MQTTClient
import machine, time

# WiFi connection assumed complete

BROKER = "broker.hivemq.com"
client = MQTTClient("pico_multi", BROKER)
client.set_last_will(b"lilex/status", b"offline")
client.connect()
client.publish(b"lilex/status", b"online")

sensor_t = machine.ADC(4)
sensor_h = machine.ADC(1)
uptime   = 0

while True:
    raw_t = sensor_t.read_u16()
    v_t   = raw_t * 3.3 / 65535
    temp  = 27 - (v_t - 0.706) / 0.001721

    raw_h = sensor_h.read_u16()
    hum   = raw_h / 65535 * 100   # simulated 0-100 %

    client.publish(b"lilex/temp",     "{:.1f}".format(temp).encode())
    client.publish(b"lilex/humidity", "{:.1f}".format(hum).encode())
    client.publish(b"lilex/uptime",   str(uptime).encode())
    print("Published t={:.1f} h={:.1f} up={}".format(temp, hum, uptime))

    time.sleep(5)
    uptime += 5

Tier 4 — Create: Full IoT pipeline — WiFi, MQTT connect with last-will, publish temp every 10 s, subscribe to /cmd and blink on "blink" payload.

from umqtt.simple import MQTTClient
import machine, network, time

SSID = "YOUR_SSID"; PASSWORD = "YOUR_PASSWORD"
MATRIC = "CB22080"   # replace with your matric number
BROKER = "broker.hivemq.com"

TOPIC_TEMP   = ("lilex/" + MATRIC + "/temp").encode()
TOPIC_CMD    = ("lilex/" + MATRIC + "/cmd").encode()
TOPIC_STATUS = ("lilex/" + MATRIC + "/status").encode()

def connect_wifi():
    wlan = network.WLAN(network.STA_IF)
    wlan.active(True)
    wlan.connect(SSID, PASSWORD)
    for _ in range(60):
        if wlan.isconnected(): return wlan
        time.sleep(0.5)
    raise OSError("WiFi timeout")

def read_temp():
    s = machine.ADC(4)
    v = s.read_u16() * 3.3 / 65535
    return 27 - (v - 0.706) / 0.001721

def on_message(topic, msg):
    if msg == b"blink":
        led = machine.Pin(25, machine.Pin.OUT)
        for _ in range(3):
            led.on(); time.sleep(0.2); led.off(); time.sleep(0.2)

wlan = connect_wifi()
print("IP:", wlan.ifconfig()[0])

client = MQTTClient("lilex_" + MATRIC, BROKER)
client.set_last_will(TOPIC_STATUS, b"offline")
client.set_callback(on_message)
try:
    client.connect()
    client.subscribe(TOPIC_CMD)
    client.publish(TOPIC_STATUS, b"online")
    while True:
        try:
            t = read_temp()
            client.publish(TOPIC_TEMP, "{:.1f}".format(t).encode())
            client.check_msg()
            print("Published {:.1f} C".format(t))
        except Exception as e:
            print("Error:", e)
        time.sleep(10)
except Exception as e:
    print("MQTT failed:", e)
